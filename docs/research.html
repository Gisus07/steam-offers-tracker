1. Fuente de datos

Principal: IStoreQueryService/Query/v1 verificado

GET https://api.steampowered.com/IStoreQueryService/Query/v1/?input_json=
{
  "query": { "start": 0, "count": 1000, "sort": 2,
    "filters": { "type_filters": { "include_games": true },
                 "price_filters": { "min_discount_percent": 1 } } },
  "context": { "language": "spanish", "country_code": "MX" },
  "data_request": { "include_basic_info": true, "include_all_purchase_options": true,
                    "include_tag_count": 20, "include_reviews": true }
}
  • Precio y descuento: best_purchase_option.original_price_in_cents, final_price_in_cents, discount_pct.
  • Fecha de fin: active_discounts[].discount_end_date (Unix).
  • Gustos: tags[{tagid, weight}]; los nombres salen de IStoreService/GetTagList, también sin key.
  • Calidad: reviews.summary_filtered.percent_positive y review_count.
  • Filtro adulto: content_descriptorids. Hace falta, porque abunda entre las ofertas baratas.
  • Tope real de 1000 ítems por página. El barrido transfiere unos 74 MB; baja mucho si se pide basic_info solo para los appids nuevos.

Riesgo: es el endpoint que usa la propia tienda y no está documentado oficialmente. Va en un adaptador aislado, con fallback.

Orden obligatorio: sin "sort": 2 (por appid), la paginación repite y saltea juegos: llegaban 10 879 distintos de 14 599. Con ese orden llegan todos verificado.

Región por usuario, barrido por país

country_code cambia moneda, precio y hasta el catálogo en oferta: el mismo día dio 14 546 juegos en US, 14 541 en AR, 14 474 en VE y 14 544 en MX verificado. Cada usuario ve su región, pero por dentro las ofertas se guardan por (appid, country) y el worker barre una vez por país con usuarios. Sumar usuarios de un mismo país no agrega requests.

Las dos opciones generan apps para iPhone. Lo que suma Expo: builds de iOS sin Mac, UI nativa también en iPhone, y menos riesgo con la guideline 4.2 de la App Store, que rechaza apps que parecen un sitio web reempaquetado.

Qué hace EAS Build para iOS docs

  1. Desde Linux o Windows corrés eas build --platform ios y el proyecto se sube a Expo.
  2. Una máquina macOS de Expo compila con Xcode y firma con tus credenciales de Apple. EAS puede generar y guardar el certificado y los provisioning profiles.
  3. Sale un .ipa. Para tu iPhone en desarrollo, registrás el teléfono con eas device:create y la build solo se instala en los dispositivos registrados. Para publicar, eas submit lo sube a TestFlight y la App Store.

Todavía no. La Mac mini con M6 arranca en 899 USD en la tienda de EE. UU. apple.com. Solo para compilar no se paga: el plan gratis de EAS alcanza, y aun contra el Starter tarda unos 47 meses en amortizarse. Lo que la justifica es lo que EAS no hace.

Conviene comprarla cuando iOS sea un canal real (usuarios que pagan o demanda validada), cuando aparezca un problema nativo que EAS no resuelve, o cuando coincida con tu próximo cambio de computadora. En ese caso, la Mac mini base con un SSD externo para proyectos y caches.

Web: separada o integrada

La web de presentación es una pieza aparte con cualquier opción: también con Capacitor, las pantallas de la app no son una landing. Lo que cambia es cuánto se comparte, y con Expo hay tres niveles:

  1. Lógica compartida: un monorepo con la app móvil, la API, la web y un paquete compartido con tipos, schemas Zod, el cliente de la API y las reglas de negocio.
  2. Componentes compartidos: con los DOM components ('use dom'), un componente React DOM se usa dentro de la app nativa y en la web tal cual docs.
  3. La app entera en web: Expo Router compila la misma app a web, con HTML estático por ruta docs.
Recomendación

Landing separada dentro del monorepo: una web de presentación necesita CSS libre, animaciones y SEO, y react-native-web es más rígido para eso. La lógica se comparte por el paquete común. Si más adelante querés la app completa en web, sale de Expo Router sin reescribirla.

4. Capa de datos y servidor

NestJS 12.3.2 compila y resuelve la inyección de dependencias con TS 7.0.2 verificado. Reylo funcionó de punta a punta con TS 7.1 beta, Nest, pg y Postgres 16 verificado, aunque tiene 4 semanas de vida, exige Node 24, necesita la base levantada para typecheckear y no hace migraciones. Prisma 8 es una reescritura completa en TypeScript que sigue en release candidate y todavía no tiene varias funciones; hoy no conviene.

TypeORM vs Drizzle probado con un spike

Comparé TypeORM 1.1.2 y Drizzle 1.0.0-rc.5 con TS 7.0.2, contra el mismo Postgres y con la misma consulta. Las dos compilan y corren. La diferencia que más importa: en TypeORM, select no achica el tipo, así que un campo no pedido compila como number y llega undefined. En Drizzle, ese mismo acceso es un error de compilación.

import 'reflect-metadata';
import { Column, DataSource, Entity, JoinColumn, ManyToOne, MoreThanOrEqual, PrimaryColumn } from 'typeorm';

@Entity('games')
export class Game {
  @PrimaryColumn('int') appid!: number;
  @Column('text') name!: string;
}

@Entity('offers')
export class Offer {
  @PrimaryColumn('int') appid!: number;
  @PrimaryColumn('char', { length: 2 }) country!: string;
  @Column('smallint', { name: 'discount_pct' }) discountPct!: number;
  @Column('int', { name: 'final_cents' }) finalCents!: number;
  @Column('int', { name: 'original_cents' }) originalCents!: number;
  @Column('timestamptz', { name: 'ends_at', nullable: true }) endsAt!: Date | null;

  @ManyToOne(() => Game)
  @JoinColumn({ name: 'appid' })
  game!: Game;
}

const ds = new DataSource({ type: 'postgres', url: process.env.DATABASE_URL, entities: [Game, Offer] });
await ds.initialize();

const offers = await ds.getRepository(Offer).find({
  where: { country: 'US', discountPct: MoreThanOrEqual(50) },
  relations: { game: true },
  select: { appid: true, discountPct: true, game: { appid: true, name: true } },
  order: { discountPct: 'DESC' },
});

// El tipo es Offer[]: `select` no achica el tipo. Esto compila...
const finalCents: number = offers[0]!.finalCents;
// ...pero en runtime vale undefined.
console.log('TypeORM', JSON.stringify(offers), '| finalCents =', finalCents);
await ds.destroy();
Código probado: Drizzle 
import { and, defineRelations, desc, eq, gte } from 'drizzle-orm';
import { drizzle } from 'drizzle-orm/node-postgres';
import { char, integer, pgTable, primaryKey, smallint, text, timestamp } from 'drizzle-orm/pg-core';

export const games = pgTable('games', {
  appid: integer('appid').primaryKey(),
  name: text('name').notNull(),
});

export const offers = pgTable('offers', {
  appid: integer('appid').notNull().references(() => games.appid),
  country: char('country', { length: 2 }).notNull(),
  discountPct: smallint('discount_pct').notNull(),
  finalCents: integer('final_cents').notNull(),
  originalCents: integer('original_cents').notNull(),
  endsAt: timestamp('ends_at', { withTimezone: true }),
}, (t) => [primaryKey({ columns: [t.appid, t.country] })]);

export const relations = defineRelations({ games, offers }, (r) => ({
  offers: { game: r.one.games({ from: r.offers.appid, to: r.games.appid }) },
}));

const db = drizzle({ connection: process.env.DATABASE_URL!, relations });

// 1) Query builder estilo SQL: el tipo sale de lo que seleccionás.
const rows = await db
  .select({ appid: offers.appid, discountPct: offers.discountPct, name: games.name })
  .from(offers)
  .innerJoin(games, eq(games.appid, offers.appid))
  .where(and(eq(offers.country, 'US'), gte(offers.discountPct, 50)))
  .orderBy(desc(offers.discountPct));

// @ts-expect-error finalCents no se seleccionó, así que no existe en el tipo.
console.log(rows[0]!.finalCents);

// 2) API relacional (equivalente a find + relations de TypeORM).
const list = await db.query.offers.findMany({
  where: { country: 'US', discountPct: { gte: 50 } },
  orderBy: { discountPct: 'desc' },
  columns: { appid: true, discountPct: true, endsAt: true },
  with: { game: { columns: { name: true } } },
});
const ends: Date | null = list[0]!.endsAt;

console.log('Drizzle select', JSON.stringify(rows));
console.log('Drizzle query ', JSON.stringify(list), '| endsAt es Date:', ends instanceof Date);
await db.$client.end();
Recomendación

Costo: es un RC, el módulo de Nest está en 0.0.2 y dejás lo conocido. Alternativa que compite: TypeORM 1.x, si preferís lo conocido y el módulo de Nest maduro.

Servidor: librerías y operación docs, npm pruebas propias donde se indica

Pensado para el VPS de 1 vCPU y 2 GB: nada que sume un servicio con estado si Postgres lo resuelve. Versiones al 1 de noviembre de 2026.

Arquitectura resultante

Postgres 18 como base, cola (pg-boss) y caché. Una imagen con dos servicios, api y worker. Un schedule por país cada 6 h en una cola exclusive con singletonKey = país. Expo Push con un job de receipts. Cloudflare Tunnel. pg_dump + rclone a B2 con restore probado.

Cambio pendiente en el modelo de datos

La app manda los eventos desde una cola sin conexión y los reintenta, así que el servidor tiene que ignorar los duplicados. Propuesta: event_uuid uuid generado en el teléfono, unique (event_uuid, occurred_at) (en una tabla particionada la clave única debe incluir occurred_at) e insert … on conflict do nothing. Probado sobre el modelo actual, con rollback: el reintento inserta 0 filas y el trigger events_state no cuenta dos veces verificado.

El acotado de occurred_at al ingresar no puede depender de now(), o el reintento cae en otra clave. Falta pasarlo a modelo-datos.sql.

Lo que toca a la app (TanStack, Expo, recetas) está en la sección Librerías del sistema de diseño.

6. Requisitos y riesgos

Ninguno impide empezar la planificación, pero varios cambian el diseño desde el primer día.

Términos de la Steam Web API verificado

  • La app no puede dar a entender que Valve o Steam la respaldan.
  • Los datos de un usuario de Steam se piden solo cuando él lo solicita. Hay que avisarle qué se guarda y en qué país, según la política de privacidad.
  • Los datos se muestran tal cual, con descargos de garantía.
  • Nada de marketing no solicitado: las notificaciones son opt-in.
  • Tope de 100 000 llamadas por día. Conviene usar una key propia también en las llamadas a Query.

Nombre y marca App Review Guidelines

Apple prohíbe usar marcas de terceros sin permiso en el nombre de la app y puede pedir que demuestres que los términos de un servicio de terceros te permiten mostrar su contenido. El nombre público no debería llevar "Steam"; la relación se explica en la descripción, con un aviso de que no hay afiliación con Valve.

Distribución en Android developer.android.com

Desde el 30 de septiembre de 2026, en Brasil, Indonesia, Singapur y Tailandia, las apps instaladas desde tiendas participantes tienen que venir de un desarrollador verificado. En 2027 eso se extiende a todo el mundo y a todas las apps en teléfonos certificados, incluido un APK instalado a mano. Para uso personal y amigos alcanza una cuenta de distribución limitada: hasta 20 dispositivos, gratis y sin documento.

Google Play: las cuentas personales nuevas necesitan una prueba cerrada con 12 testers durante 14 días antes de publicar no verificado.

Para la planificación

  • Historial de precios como cambios: guardar intervalos de precio, no snapshots completos, que serían unos 21 millones de filas por país y año.
  • Monitoreo de la fuente: validar cada respuesta de Steam y compararla con el barrido anterior; si algo cambia, alertar y pasar al fallback.
  • Backups de Postgres fuera del VPS.
  • Dominio con TLS para el login de Steam, la landing, los links de la app y la política de privacidad.
  • Modelo de negocio sin anuncios invasivos: define qué se construye y si hace falta cobrar dentro de la app.
  • Idiomas y zonas horarias para las fechas de fin.
