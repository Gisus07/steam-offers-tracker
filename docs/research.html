Veredicto

Steam expone un endpoint sin API key, IStoreQueryService/Query, que devuelve todos los juegos en oferta con precio original y final, porcentaje, fecha de fin y tags ponderadas. Un barrido completo por país cuesta 15 requests. Reemplaza entero al Puppeteer con scroll infinito de la v1.

Correcciones a la revisión 1

Expo no está en el SDK 56: el actual es el SDK 58 (29 de septiembre, React Native 0.88). Los content mappers de TS 7.1 ya tienen un uso concreto, Reylo, que está en la sección 4.

1. Fuente de datos

Principal: IStoreQueryService/Query/v1 verificado

GET https://api.steampowered.com/IStoreQueryService/Query/v1/?input_json=
{
  "query": { "start": 0, "count": 1000,
    "filters": { "type_filters": { "include_games": true },
                 "price_filters": { "min_discount_percent": 1 } } },
  "context": { "language": "spanish", "country_code": "MX" },
  "data_request": { "include_basic_info": true, "include_all_purchase_options": true,
                    "include_tag_count": 20, "include_reviews": true }
}
  • Precio y descuento: best_purchase_option.original_price_in_cents, final_price_in_cents, discount_pct.
  • Fecha de fin: active_discounts[].discount_end_date (Unix).
  • Gustos: tags[{tagid, weight}]; los nombres salen de IStoreService/GetTagList, también sin key.
  • Calidad: reviews.summary_filtered.percent_positive y review_count.
  • Filtro adulto: content_descriptorids. Hace falta, porque abunda entre las ofertas baratas.
  • Tope real de 1000 ítems por página. El barrido transfiere unos 74 MB; baja mucho si se pide basic_info solo para los appids nuevos.

Riesgo: es el endpoint que usa la propia tienda y no está documentado oficialmente. Va en un adaptador aislado, con fallback.

Con varios usuarios, el costo crece por país

country_code cambia moneda, precio y hasta el catálogo en oferta: el mismo día dio 14 546 juegos en US, 14 541 en AR, 14 474 en VE y 14 544 en MX verificado. Las ofertas se guardan por (appid, country) y el worker barre una vez por país con usuarios. Con 10 países son unas 150 requests por barrido, y sumar usuarios de un mismo país no agrega ninguna.

Detectar ofertas nuevas

Ningún endpoint marca cuándo empezó una oferta. Se guarda un snapshot y se compara con el siguiente por (appid, country, discount_end_date): lo que aparece es nuevo, lo que desaparece terminó, y un cambio de discount_pct significa que bajó más. Con un barrido cada 6 h alcanza.

Recomendación

Expo SDK 58. Cumple el objetivo de aprender otro paradigma, renderiza UI nativa en lugar de una WebView (Capacitor se parece a una PWA en sensación y rendimiento) y los módulos que hacen falta son oficiales. Con Drizzle sobre expo-sqlite, el móvil y el backend usan el mismo ORM.

Costo: un upgrade de SDK cada 1 a 3 meses si querés estar al día, y Metro en lugar de Vite. Capacitor solo ganaría si quisieras compartir código con un panel web.

3. Multiusuario y recomendador

Global (compartido)Por usuario
games: tags con peso, reviews, descriptoresusers: SteamID64 vía OpenID
offers por (appid, country) + historialuser_settings: país, % mínimo, contenido excluido, horario y tope diario
tags: nombre por idiomadevices: tokens de push
events append-only, user_profiles, notifications_sent
  • Desde el día 1: filtrado por contenido para cada usuario. Cada juego es un vector de tags ponderadas (TF-IDF) más precio, descuento y reviews. El perfil decae con w·e^(−edad/τ), con τ entre 60 y 90 días.
  • Con varios usuarios: se agrega filtrado colaborativo item-item y se arma un híbrido que pondera cada parte según cuánto historial tenga cada persona.
  • Exploración: entre el 10 y el 20 % del feed queda fuera del perfil.
  • Arranque en frío: biblioteca, wishlist y tags elegidas en el onboarding.
  • Pulirlo: registrar impresiones permite medir CTR, precision@k y NDCG, y comparar variantes por cohortes (A/B).
  • Dónde corre: en el backend. El móvil guarda los eventos en una cola SQLite y los sube en lotes, así funciona offline.
  • Notificaciones: en cada barrido, las ofertas nuevas de un país se cruzan con los usuarios de ese país, se puntúan con su perfil, se filtran por sus umbrales, se descartan las ya enviadas y salen por FCM en lote.

4. Capa de datos y stack

NestJS con TypeScript 7 verificado

NestJS 12.3.2 compila con TS 7.0.2 usando experimentalDecorators y emitDecoratorMetadata, y la inyección de dependencias resuelve bien. TS 7.0.2 es el estable desde julio; la 7.1 está en beta.

Reylo probado con un spike

Permite importar archivos .sql desde TypeScript con tipos inferidos desde la base de datos real, usando los content mappers de TS 7.1, sin codegen. Lo probé con Reylo 0.6.0, TS 7.1 beta, NestJS 12, pg, Postgres 16 y Node 24.

PruebaResultado
Inferencia de filasCorrecta: { appid: number; name: string; ... }
CardinalidadQuery por PK → Row | null; listado → Row[]
Columna mal escritaError de tipos dentro del propio .sql
timestamptzTipado como string ISO, no Date; el typecheck me marcó el supuesto equivocado
Dentro de un servicio Nest con DIFunciona, compilando con tsc y corriendo con --import reylo/register
Tiempo de typecheck~12 s en frío, ~0,2 s sin cambios, ~4,7 s tras editar un .sql

Límites: es la versión 0.6, con 4 semanas de vida, y depende de TS 7.1 beta. Exige Node 24, necesita la base levantada para typecheckear (también en CI) y no hace migraciones. Tampoco sirve en el cliente móvil, porque no tiene plugin para Metro.

Prisma: lo reescribieron docs

Prisma 8 es una reescritura completa en TypeScript y sigue en release candidate; desde agosto, npm install prisma sin versión instala el RC. Cambia el esquema (ahora es un "contract"), la CLI y la forma de las queries. Todavía le faltan $extends, el incremento atómico, la mayoría de los nested writes y los niveles de aislamiento. Prisma 7 queda en mantenimiento por 18 meses. Hoy no conviene para este proyecto.

Recomendación preliminar

Drizzle como base y Reylo para las queries pesadas del backend. Drizzle se encarga del esquema, las migraciones y el CRUD, y es el mismo ORM en el móvil sobre expo-sqlite. Reylo cubre el SQL complejo del recomendador, tipado contra la base real. Si Reylo cambia de API, esas queries pasan al sql de Drizzle sin tocar el resto.

Alternativa: todo SQL-first con Reylo y migraciones SQL planas. Es más puro, pero no resuelve el ORM del móvil.

5. VPS

Postgres, la API y el worker consumen entre 400 y 700 MB de RAM al inicio. Con 2 GB alcanza para arrancar; 4 GB da margen para varios usuarios.

Hetzner CX23 no verificado

2 vCPU y 4 GB por entre 3,49 y 5,49 €/mes después de las subidas de 2026, más 0,50 € por la IPv4. No tiene región en LatAm, pero para esta app la latencia importa poco. A precio regular, Hostgator NVMe 2 sale más caro y trae la mitad de RAM. A precio promo quedan parejos, pero Hostgator te ata a pagar años por adelantado.
