Veredicto

Steam expone un endpoint sin API key, IStoreQueryService/Query, que devuelve todos los juegos en oferta con precio original y final, porcentaje, fecha de fin y tags ponderadas. Un barrido completo cuesta 15 requests. La v1 necesitaba Puppeteer con scroll infinito; esto lo reemplaza entero.

1. Fuente de datos

Principal: IStoreQueryService/Query/v1 verificado

GET https://api.steampowered.com/IStoreQueryService/Query/v1/?input_json=
{
  "query": { "start": 0, "count": 1000,
    "filters": { "type_filters": { "include_games": true },
                 "price_filters": { "min_discount_percent": 1 } } },
  "context": { "language": "spanish", "country_code": "VE" },
  "data_request": { "include_basic_info": true, "include_all_purchase_options": true,
                    "include_tag_count": 20, "include_reviews": true }
}
  • Precio y descuento: best_purchase_option.original_price_in_cents, final_price_in_cents, discount_pct.
  • Fecha de fin: active_discounts[].discount_end_date (Unix).
  • Gustos: tags[{tagid, weight}]; nombres con IStoreService/GetTagList, también sin key.
  • Calidad: reviews.summary_filtered.percent_positive y review_count.
  • Filtro adulto: content_descriptorids. Hace falta, porque abunda entre las ofertas baratas.
  • Moneda regional con country_code (probado US, AR, VE y MX).
  • Tope real de 1000 ítems por página: si pedís 5000, devuelve 1000. El barrido completo transfiere unos 74 MB; se reduce pidiendo basic_info solo para los appids nuevos.

Riesgo: no está documentado oficialmente, porque es el endpoint que usa la propia tienda. Va en un adaptador aislado, con fallback.

Detectar ofertas nuevas

Ningún endpoint marca cuándo empezó una oferta. La solución es guardar un snapshot y compararlo con el siguiente por (appid, discount_end_date): lo que aparece es una oferta nueva, lo que desaparece terminó, y un cambio de discount_pct significa que bajó más. Con un barrido cada 6 h alcanza.

Señales iniciales de gustos

  • IPlayerService/GetOwnedGames (biblioteca y horas jugadas) pide key: sin ella devuelve 401 verificado. Para tener key, la cuenta tiene que haber gastado al menos 5 USD, y el tope es de 100 k llamadas por día docs.
  • IWishlistService/GetWishlist no pediría key en perfiles públicos no verificado. Hay que probarlo con tu SteamID.

Recomendación

Un solo front en React (Vite) que se publica como PWA y se empaqueta como APK con Capacitor, con push por FCM. Usa tu stack, no depende de Telegram y le da al recomendador todas las señales.

Alternativa que compite: bot de Telegram con Mini App. Usa la misma UI en React y no requiere infraestructura de push ni build de APK. El costo es depender de Telegram.

3. Recomendador

Para un solo usuario, el filtrado basado en contenido es suficiente; el colaborativo no aplica. Cada juego se representa como un vector de tags de Steam ponderadas (TF-IDF sobre unas 450 tags). El perfil es la suma ponderada de los juegos con los que interactuaste, con decaimiento w·e^(−edad/τ) y τ entre 60 y 90 días. El ranking combina la similitud coseno con el descuento, las reseñas y la cercanía de la fecha de fin.

  • Exploración: entre el 10 y el 20 % del feed queda fuera del perfil (epsilon-greedy o Thompson sampling por cluster de tags), para no encerrarte en una burbuja.
  • Arranque en frío: biblioteca con horas jugadas más la wishlist de Steam.
  • Infraestructura: unos 15 k juegos entran en memoria o en SQL plano. pgvector solo tendría sentido con embeddings de las descripciones.

4. Stack

  • TypeScript 7.1 sí tiene content mappers (beta del 20 de octubre de 2026) docs. Yo había dudado de que existieran y me equivoqué. Pero no mapean datos: son un punto de extensión para que tsc type-checkee archivos .vue, .svelte, Astro o MDX. No reemplazan a Prisma, Drizzle, Kysely ni a Zod o Valibot.
  • Consumo estimado de Postgres, API y worker: entre 400 y 700 MB de RAM. Lo más pesado es la transferencia del barrido, no la CPU.
  • VPS: Hetzner CX23 (2 vCPU y 4 GB) cuesta unos 5,49 €/mes después de las subidas de 2026 no verificado.
